# Conventions

## Bash Shell Scripts

- Use bash strict mode in every shell script: `#!/usr/bin/env bash` and `set -euo pipefail`.
- Write feature installers as entrypoint scripts that run as root.
- Follow the repository’s standard structure for each script type and keep related scripts consistent in filenaming, layout, style, sections, conventions and patterns used.
- All log messages, including output and error messages, should be handled consistently for all script instances.
- Separate section header comments from ordinary comments with a blank line.
- Place comments that describe a code block immediately above that block.
- Prefer comments that explain intent or non-obvious decisions rather than restating obvious code.
- Prefer small, focused helpers and keep logic readable rather than over-abstracting.
- Do not use TRAP or defensively program for unlikely/rare conditions.
- Perform explicit checks for option inputs, compatibility, prerequisites, outputs etc as required or appropriate for the specific type/class of script.
- To mitigate the risk of consuming poisoned packages, configurable `npm` and `pipx` installations default their respective `--min-release-age` and `--cooldown` options to seven days.
- Use lowercase `snake_case` for shell variables.

### Bash Linting

- Use `shellcheck --enable=all` to lint shell scripts.

### Bash Formatting

- Use `shfmt -i 4 -ci -w` to format shell scripts.

### Feature Installation Scripts

- Keep feature installer scripts in the same section order and headings:
  1. Inputs
  2. Collect options
  3. Logging functions
  4. Check option compatibility
  5. Prerequisites
  6. Check required commands
  7. Installation
  8. Install functions
  9. Install packages
- Read feature options once into normalized local variables before use.
- Consume options from uppercase environment variables that are populated from `devcontainer-feature.json`.
- Make each declared option change installer behavior. If a capability cannot be implemented by the feature specification, keep it in the consuming `devcontainer.json` instead.
- Use the shared `log`, `error`, and `require_command` helpers unless a script has a clear reason to do otherwise.
- Installers that invoke `apt` directly should implement a shared `install_apt_packages` helper.
- `install_apt_packages` should perform one complete `apt` cycle: `apt-get update`, `apt-get install -y --no-install-recommends`, `apt-get clean`, and removal of `/var/lib/apt/lists/*`.
- Fail early with a clear message when an optional capability requires a missing prerequisite.
- Use `npm` global installs with `--global --ignore-scripts` and, when configured, `--min-release-age`.
- Use pipx's `--cooldown` argument for constrained `pipx` installs when configured.

### Feature Test Scripts

- Keep feature test scripts in the same section order and headings:
  1. Inputs
  2. Prerequisites
  3. Tests
- Use `source dev-container-features-test-lib` in test scripts before running checks.
- Prefer concrete assertions that verify real behavior and call `reportResults` at the end.

## Feature Declarations

- Expose feature options through `devcontainer-feature.json` and consume them in `install.sh`.
- Represent string list options as space-separated lists; preserve commas as part of individual values.
- Keep feature options limited to behavior the Feature specification can implement.
- Treat host mounts, user configuration, and similar host-side concerns as the responsibility of the consuming `devcontainer.json`.
- Reserve `installsAfter` for portable, published-feature dependencies.

## Feature Test Scenarios

- Use `ubuntu:latest` for scenario and integration coverage.
- When a scenario depends on `Node.js`, compose the local `node` feature explicitly in the test setup.
- When a scenario depends on `pipx`, compose the local `apt-python` feature and enable the `installPipx` option explicitly in the test setup.
- For autogenerated isolated tests, retain a base image where the Dev Container CLI cannot express an required feature composition.
- For local test composition in this repository, use `overrideFeatureInstallOrder` when local features must be installed before dependent features.

## Feature Testing

- Use `./scripts/test.sh` to test feature changes and the `_global` integration test. This script is a token-efficient wrapper for running common `devcontainer features test ...` commands. It captures detailed output in a temporary log file and prints the test report.
- Test selected changed features with `./scripts/test.sh <feature> [feature ...]`.
- Test only the `_global` integration scenarios with `./scripts/test.sh --global`.
- Test all feature and `_global` scenarios with `./scripts/test.sh`.
- Run the relevant feature tests and the `_global` integration test before completing changes that can affect integration behavior. Report the summarised results.

## Documentation

- Use `devcontainer features generate-docs --project-folder src --namespace serialprimate/ubuntu-devcontainer-features` to (re)generate all feature `README.md` files from both feature `devcontainer-feature.json` and optional `NOTES.md` when they change.
- Keep each feature's `README.md` (generated) and `NOTES.md` consistent with the feature's declaration or implementation details.
- Keep the global `README.md` consistent with all features and their descriptions.

### Markdown Linting

- Do not lint the generated feature `README.md` files.
- Use `markdownlint-cli2 --config .markdownlint-cli2.jsonc` to lint markdown files.
- Use `markdownlint-cli2 --config .markdownlint-cli2.jsonc "**/*.md" "#src/*/README.md"` to lint all markdown files except for the generated feature `README.md` files.

## Temporary Files

- Write temporary files to `/tmp/<repo-name>/` and remove them when no longer needed.

## Docker Resources

- Remove outdated/superceded Docker resources (images, containers, volumes, networks, etc) when no longer needed.
